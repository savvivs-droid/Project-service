# Project Service — приложение для сервиса ремонта гастрооборудования

Flutter-приложение для сервисной компании, обслуживающей кухонное
оборудование в кафе, ресторанах и фастфудах. Backend — Supabase
(база данных, авторизация, хранение фото, push-уведомления).

Одно приложение, две роли:
- **Клиент** — ответственный в заведении, регистрируется в приложении
  самостоятельно, создаёт заявки на ремонт.
- **Администратор** — сотрудник сервисной компании, обрабатывает заявки
  всех заведений, назначает время визита. Администраторов в приложении
  не регистрируют — их заводят вручную (см. Шаг 5).

## Структура проекта

```
lib/

    config/app_config.dart      # чтение SUPABASE_URL и SUPABASE_ANON_KEY из .env

    theme/app_theme.dart
  models/                       # Dart-классы, соответствующие таблицам БД
  services/
    supabase_service.dart       # инициализация клиента Supabase
    auth_repository.dart        # вход, регистрация клиента, выход
    ares_service.dart           # запрос к чешскому реестру ARES по IČO
    profile_repository.dart     # получение профиля текущего пользователя
  features/
    auth/                       # экраны входа и регистрации
    home/                       # главные экраны клиента и администратора (пока заглушки)
  main.dart
supabase/
  schema.sql                    # вся схема БД: таблицы, RLS-политики, триггеры
```

## Шаг 0. Сгенерировать платформенные папки (один раз, локально)

Этот проект написан без Flutter SDK (в текущем облачном окружении его нет),
поэтому папок `android/`, `ios/`, `web/` и т.п. ещё не существует — их
генерирует сама команда Flutter. Сделайте это один раз у себя на
компьютере, где установлен Flutter:

```bash
git clone <ваш форк репозитория>
cd Project-service
flutter create . --org com.yourcompany --project-name project_service
```

Команда допишет недостающие платформенные файлы, не трогая уже
написанный код в `lib/`. После этого закоммитьте и запушьте появившиеся
папки — дальше они уже будут в репозитории как обычно.

## Шаг 1. Создать проект в Supabase

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте
   новый проект (Organization → New Project).
2. Дождитесь, пока проект поднимется (обычно 1-2 минуты).
3. Откройте **Project Settings → API** и скопируйте:
   - `Project URL` → это будет `SUPABASE_URL`
   - `anon public` ключ → это будет `SUPABASE_ANON_KEY`

## Шаг 2. Настроить .env

```bash
cp .env.example .env
```

Откройте `.env` и вставьте значения из шага 1:

```
SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi...
```

Файл `.env` добавлен в `.gitignore` — он никогда не попадёт в git.
Каждый разработчик и каждое окружение (dev/prod) настраивает свой `.env`.

## Шаг 3. Применить схему базы данных

1. В Supabase Dashboard откройте **SQL Editor → New query**.
2. Скопируйте содержимое файла `supabase/schema.sql` целиком и вставьте.
3. Нажмите **Run**.

Что делает этот файл (коротко, подробные комментарии — прямо в файле):

- Создаёт таблицы под все сущности: `establishments` (заведения),
  `profiles` (пользователи), `equipment` (оборудование),
  `service_requests` (заявки), `service_request_equipment` (связь
  заявки с несколькими единицами оборудования — заявка может касаться
  сразу нескольких приборов), `repair_history` (история ремонта).
- Включает **Row Level Security (RLS)** на каждой таблице — это
  встроенный в Postgres механизм, который фильтрует строки на уровне
  базы данных в зависимости от того, кто делает запрос. Даже если в
  коде приложения будет ошибка, клиент физически не сможет прочитать
  чужие заявки или оборудование чужого заведения — база данных это не
  отдаст.
  - Клиент видит и редактирует только данные своего заведения
    (`establishment_id`, взятый из его профиля).
  - Администратор видит и может менять всё.
- Настраивает автоматическое создание заведения и профиля клиента при
  регистрации (см. следующий раздел).

## Шаг 4. Как устроена регистрация

Регистрация в приложении — **только для клиентов, и только
самостоятельная**. Отдельного выбора роли на экране нет: любой, кто
регистрируется через приложение, становится клиентом — это решает
сервер, а не форма. Администраторов через приложение не заводят вообще
(см. Шаг 5).

При регистрации клиент вводит свои данные (имя, телефон, email, пароль)
и данные своего заведения: **IČO** (с автоподстановкой названия и
адреса из чешского реестра ARES, см. `ares_service.dart`), адрес и
контактный телефон заведения.

⚠️ Учтите: это открывает регистрацию для всех, у кого есть ссылка на
приложение — заявки от новых заведений стоит первое время проверять
вручную, пока нет отдельного шага подтверждения администратором.

Как это работает технически:

1. Приложение вызывает `supabase.auth.signUp(...)`, передавая имя,
   телефон и данные заведения (`new_establishment_name`,
   `new_establishment_address`, `new_establishment_contact_phone`,
   `new_establishment_ico`) как метаданные пользователя.
2. В базе данных срабатывает триггер `handle_new_user` (описан в
   `schema.sql`, раздел 6): он создаёт запись в `establishments` и
   профиль пользователя с ролью `client`, привязанный к этому
   заведению. Если с таким IČO заведение уже зарегистрировано —
   регистрация отменяется с понятной ошибкой.

## Шаг 5. Создать администраторов

Через приложение регистрируются только клиенты (см. Шаг 4), поэтому
каждого администратора заводят вручную (это описано и в конце
`schema.sql`). Повторите эти шаги для каждого администратора —
у вас их будет два.

⚠️ Важно: триггер `handle_new_user` (см. раздел 6 в `schema.sql`) срабатывает
на **любое** добавление строки в `auth.users`, включая создание пользователя
вручную через Dashboard — а там кода приглашения нет. Без обхода этого
триггера Dashboard молча откажет с ошибкой "failed to create user".

Отключить сам триггер через `alter table auth.users disable trigger ...`
не получится — таблицей `auth.users` в Supabase владеет системная роль,
а не ваш аккаунт, и SQL Editor выполняет запросы не от её имени. Зато
функцией `handle_new_user()`, которую вызывает триггер, владеете вы —
её можно свободно менять. Поэтому временно превращаем её в пустышку:

1. В **SQL Editor** выполните:

   ```sql
   create or replace function public.handle_new_user()
   returns trigger
   language plpgsql
   security definer
   set search_path = public
   as $$
   begin
     return new;
   end;
   $$;
   ```

2. В Supabase Dashboard: **Authentication → Users → Add user** — создайте
   пользователя с email и паролем. Теперь должно пройти без ошибки.
3. Скопируйте его `id` (uuid) из списка пользователей.
4. В **SQL Editor** выполните одним запросом (обязательно вместе — если
   выполнить только `insert`, функция останется пустышкой, и обычная
   регистрация клиентов в приложении перестанет создавать профили):

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
declare
  v_establishment_id uuid;
  v_establishment_name text;
  v_ico text;
begin
  v_establishment_name := new.raw_user_meta_data ->> 'new_establishment_name';

  if v_establishment_name is null then
    raise exception 'Отсутствуют данные заведения для регистрации клиента';
  end if;

  v_ico := nullif(new.raw_user_meta_data ->> 'new_establishment_ico', '');

  if v_ico is not null
     and exists (select 1 from public.establishments where ico = v_ico)
  then
    raise exception 'Заведение с таким IČO уже зарегистрировано в системе';
  end if;

  insert into public.establishments (name, address, contact_phone, ico)
  values (
    v_establishment_name,
    new.raw_user_meta_data ->> 'new_establishment_address',
    new.raw_user_meta_data ->> 'new_establishment_contact_phone',
    v_ico
  )
  returning id into v_establishment_id;

  insert into public.profiles (id, full_name, phone, role, establishment_id)
  values (
    new.id,
    new.raw_user_meta_data ->> 'full_name',
    new.raw_user_meta_data ->> 'phone',
    'client',
    v_establishment_id
  );

  return new;
end;
$$;

insert into public.profiles (id, full_name, phone, role)
values ('<uuid пользователя>', 'Имя Фамилия', '+70000000000', 'admin');
```

Если этот запрос упадёт с ошибкой (например, из-за опечатки в uuid) —
запустите весь блок заново целиком: если хотя бы одна строка внутри
не выполнится, Supabase откатывает весь запрос, включая восстановление
функции.

Теперь этим email/паролем можно войти в приложение как администратор.

## Шаг 6. Запустить приложение

```bash
flutter pub get
flutter run
```

Откроется экран входа. Войдите под администратором из шага 5, либо
зарегистрируйте нового клиента через экран регистрации.

## Быстрый предпросмотр без установки Flutter (веб-сборка)

Если под рукой нет компьютера с Flutter — можно собрать веб-версию и
открыть её как обычный сайт (например, через GitHub Pages). Команда сборки:

```bash
flutter build web --release --base-href /<имя-репозитория>/ --no-web-resources-cdn
```

Две вещи, без которых веб-сборка на GitHub Pages показывает пустой белый
экран (проверено на практике):

- **`--no-web-resources-cdn`** — без этого флага рендер-движок CanvasKit
  подгружается с внешнего `gstatic.com`; если этот домен недоступен
  (блокировка сети/оператора), приложение зависает на пустом экране.
  Флаг заставляет использовать CanvasKit, уже включённый в саму сборку.
- **Файл `.nojekyll`** в корне опубликованной ветки — GitHub Pages по
  умолчанию прогоняет статику через Jekyll, который может некорректно
  отдавать `.wasm` и прочие не-HTML файлы. Пустой файл `.nojekyll`
  отключает эту обработку.

Также для GitHub Pages на бесплатном тарифе репозиторий должен быть
публичным (`Settings → General → Danger Zone → Change visibility`).
