# Project Service — приложение для сервиса ремонта гастрооборудования

Flutter-приложение для сервисной компании, обслуживающей кухонное
оборудование в кафе, ресторанах и фастфудах. Backend — Supabase
(база данных, авторизация, хранение фото, push-уведомления).

Одно приложение, три роли:
- **Клиент** — ответственный в заведении, создаёт заявки на ремонт.
- **Диспетчер** — обрабатывает заявки всех заведений, назначает время.
- **Администратор** — то же, что диспетчер, плюс управление заведениями,
  сотрудниками и кодами приглашений.

## Структура проекта

```
lib/

    config/app_config.dart      # чтение SUPABASE_URL и SUPABASE_ANON_KEY из .env
    constants/                  # enum-ы роли, статуса заявки, статуса оборудования
    theme/app_theme.dart
  models/                       # Dart-классы, соответствующие таблицам БД
  services/
    supabase_service.dart       # инициализация клиента Supabase
    auth_repository.dart        # вход, регистрация по коду приглашения, выход
    profile_repository.dart     # получение профиля текущего пользователя
  features/
    auth/                       # экраны входа и регистрации
    home/                       # главные экраны для каждой роли (пока заглушки)
  main.dart
supabase/
  schema.sql                    # вся схема БД: таблицы, RLS-политики, триггеры
```

## Шаг 0. Сгенерировать платформенные папки (один раз, локально)

Этот проект написан без Flutter SDK (в текущем облачном окружении его нет),
поэтому папок `android/`, `ios/`, `web/` и т.п. ещё не существует — их
генерирует сама команда Flutter. Сделайте это один раз у себя на
компьютере, где установлен Flutter:

```bash
git clone <ваш форк репозитория>
cd Project-service
flutter create . --org com.yourcompany --project-name project_service
```

Команда допишет недостающие платформенные файлы, не трогая уже
написанный код в `lib/`. После этого закоммитьте и запушьте появившиеся
папки — дальше они уже будут в репозитории как обычно.

## Шаг 1. Создать проект в Supabase

1. Зарегистрируйтесь на [supabase.com](https://supabase.com) и создайте
   новый проект (Organization → New Project).
2. Дождитесь, пока проект поднимется (обычно 1-2 минуты).
3. Откройте **Project Settings → API** и скопируйте:
   - `Project URL` → это будет `SUPABASE_URL`
   - `anon public` ключ → это будет `SUPABASE_ANON_KEY`

## Шаг 2. Настроить .env

```bash
cp .env.example .env
```

Откройте `.env` и вставьте значения из шага 1:

```
SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
SUPABASE_ANON_KEY=eyJhbGciOi...
```

Файл `.env` добавлен в `.gitignore` — он никогда не попадёт в git.
Каждый разработчик и каждое окружение (dev/prod) настраивает свой `.env`.

## Шаг 3. Применить схему базы данных

1. В Supabase Dashboard откройте **SQL Editor → New query**.
2. Скопируйте содержимое файла `supabase/schema.sql` целиком и вставьте.
3. Нажмите **Run**.

Что делает этот файл (коротко, подробные комментарии — прямо в файле):

- Создаёт таблицы под все сущности: `establishments` (заведения),
  `profiles` (пользователи), `equipment` (оборудование),
  `service_requests` (заявки), `service_request_equipment` (связь
  заявки с несколькими единицами оборудования — заявка может касаться
  сразу нескольких приборов), `repair_history` (история ремонта),
  `invite_codes` (коды приглашений).
- Включает **Row Level Security (RLS)** на каждой таблице — это
  встроенный в Postgres механизм, который фильтрует строки на уровне
  базы данных в зависимости от того, кто делает запрос. Даже если в
  коде приложения будет ошибка, клиент физически не сможет прочитать
  чужие заявки или оборудование чужого заведения — база данных это не
  отдаст.
  - Клиент видит и редактирует только данные своего заведения
    (`establishment_id`, взятый из его профиля).
  - Диспетчер и администратор видят и могут менять всё.
- Настраивает автоматическое создание профиля пользователя при
  регистрации (см. следующий раздел про коды приглашений).

## Шаг 4. Как устроена регистрация и коды приглашений

Ключевое решение по безопасности: **пользователь не может сам назначить
себе роль**, даже если в интерфейсе регистрации есть переключатель
"Клиент / Диспетчер / Админ". Этот переключатель — только подсказка,
которая меняет текст на экране. Настоящую роль и `establishment_id`
всегда определяет **код приглашения**, а код создаётся заранее
сотрудником компании в базе данных.

Как это работает технически:

1. Администратор или диспетчер создаёт запись в таблице `invite_codes`
   (пока это делается вручную через Table Editor в Supabase — экран
   генерации кодов в приложении появится на одном из следующих этапов),
   указывая роль (`client`/`dispatcher`/`admin`) и, для клиента,
   `establishment_id` — то есть к какому заведению привязать код.
2. Пользователь в приложении вводит email, пароль и этот код на экране
   регистрации.
3. Приложение вызывает `supabase.auth.signUp(...)`, передавая код,
   имя и телефон как метаданные пользователя.
4. В базе данных срабатывает триггер `handle_new_user` (описан в
   `schema.sql`): он проверяет код, создаёт профиль пользователя с
   ролью и заведением **из кода**, и помечает код использованным.
   Если код неверный, уже использован или просрочен — регистрация
   целиком отменяется, и приложение покажет ошибку.

Пример: чтобы пригласить клиента из кафе «Ромашка», выполните в SQL
Editor (после того как создали заведение в таблице `establishments`):

```sql
insert into public.invite_codes (code, role, establishment_id)
values ('ROMASHKA-1', 'client', '<id заведения Ромашка>');
```

## Шаг 5. Создать первого администратора

Коды приглашений создают только сотрудники — а самому первому сотруднику
код выдать некому. Поэтому первого администратора нужно создать вручную
(это описано и в конце `schema.sql`).

⚠️ Важно: триггер `handle_new_user` (см. раздел 6 в `schema.sql`) срабатывает
на **любое** добавление строки в `auth.users`, включая создание пользователя
вручную через Dashboard — а там кода приглашения нет. Без обхода этого
триггера Dashboard молча откажет с ошибкой "failed to create user".

Отключить сам триггер через `alter table auth.users disable trigger ...`
не получится — таблицей `auth.users` в Supabase владеет системная роль,
а не ваш аккаунт, и SQL Editor выполняет запросы не от её имени. Зато
функцией `handle_new_user()`, которую вызывает триггер, владеете вы —
её можно свободно менять. Поэтому временно превращаем её в пустышку:

1. В **SQL Editor** выполните:

   ```sql
   create or replace function public.handle_new_user()
   returns trigger
   language plpgsql
   security definer
   set search_path = public
   as $$
   begin
     return new;
   end;
   $$;
   ```

2. В Supabase Dashboard: **Authentication → Users → Add user** — создайте
   пользователя с email и паролем. Теперь должно пройти без ошибки.
3. Скопируйте его `id` (uuid) из списка пользователей.
4. В **SQL Editor** выполните одним запросом (обязательно вместе — если
   выполнить только `insert`, функция останется пустышкой, и обычная
   регистрация по коду в приложении перестанет создавать профили):

```sql
create or replace function public.handle_new_user()
returns trigger
language plpgsql
security definer
set search_path = public
as $$
declare
  v_invite public.invite_codes%rowtype;
begin
  select * into v_invite
  from public.invite_codes
  where code = new.raw_user_meta_data ->> 'invite_code'
    and used_by is null
    and (expires_at is null or expires_at > now())
  for update;

  if v_invite is null then
    raise exception 'Код приглашения недействителен, уже использован или просрочен';
  end if;

  insert into public.profiles (id, full_name, phone, role, establishment_id)
  values (
    new.id,
    new.raw_user_meta_data ->> 'full_name',
    new.raw_user_meta_data ->> 'phone',
    v_invite.role,
    v_invite.establishment_id
  );

  update public.invite_codes
  set used_by = new.id, used_at = now()
  where code = v_invite.code;

  return new;
end;
$$;

insert into public.profiles (id, full_name, phone, role)
values ('<uuid пользователя>', 'Имя Фамилия', '+70000000000', 'admin');
```

Если этот запрос упадёт с ошибкой (например, из-за опечатки в uuid) —
запустите весь блок заново целиком: если хотя бы одна строка внутри
не выполнится, Supabase откатывает весь запрос, включая восстановление
функции.

Теперь этим email/паролем можно войти в приложение как администратор.

```bash
flutter pub get

```
